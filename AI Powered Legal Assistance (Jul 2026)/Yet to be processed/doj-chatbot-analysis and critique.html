Paper Review · IJIRCCE · Vol 13, Issue 5, May 2025

The DOJ Chatbot Paper, Unpacked

A working critique of "Developing an AI Based Interactive Chatbot for the Department of Justice's Website" — what was actually built (versus proposed), how current the ideas are, and what's worth carrying into "Your Legal."

Authors

Manoj L, Monika Yadav A, Vachanashree, Dr. Zafar Ali Khan — Presidency University, Bengaluru

Venue

IJIRCCE, May 2025

Stated stack

NLP · OpenAI API · Dialogflow · LLMs (all conceptual)

Read this first

This paper is a design proposal and literature survey, not a report on a built and tested system. There is no code, no deployed chatbot, no dataset, and no evaluation — every claim in Sections III–V is written in future/conditional tense ("we'd need to," "we should," "the chatbot would"). Treat the findings below accordingly.

01

Architecture

Two architecture figures are given, and they don't agree with each other or with the rest of the paper's tech claims.

FigureFlow shownIssue
Fig. 1 — "Workflow Architecture"User → UI → Language Selection → Message Processing (NLP) → Decision: Local Data vs. OpenAI API Call → Response Generation → OutputGeneric enough to describe almost any retrieval-or-LLM-fallback chatbot; no legal-specific step (no citation checking, no source linking, no jurisdiction handling)
Fig. 2 — "Chatbot System Overview"End-User → "Symptoms" → Dialogflow → Intent Matching → External API → Database → "Diagnosis" → ResponseLabels ("Symptoms," "Diagnosis") are medical-chatbot terminology, not legal — this diagram appears to be reused from an unrelated (likely healthcare) chatbot template without being adapted to the DOJ domain

The only architectural decision actually explained in prose is a local-knowledge-base-first, OpenAI-API-fallback pattern (Section 3.4–3.5): check an internal FAQ/knowledge base first, and only call an external LLM if nothing local matches. That's a sound, cost-aware pattern — but it's described at a conceptual level with no schema, no retrieval mechanism, no confidence threshold, and no detail on what "local data" actually contains.

Read this as

A one-paragraph architectural sketch (hybrid local-lookup + LLM fallback) stretched across two inconsistent diagrams — one of which wasn't built for this project.

02

How outdated is the tech stack?

Directionally current Never implemented or version-pinned

Unlike the LAWBOT paper, this one at least names LLM-era components — but because nothing was built, there's no way to judge how well any of it was actually used.

  • OpenAI API + LLMs are named as the fallback layer (Section 3.4), which is a reasonable 2025 choice — but no model is specified (GPT-4? GPT-4o? a fine-tuned model?), no prompt design is shown, and no retrieval-augmentation (RAG) is implemented despite RAG being repeatedly praised in their own literature survey (ref. [1], [21]).
  • Dialogflow appears in Fig. 2 and the "Core Chatbot Development Techniques" list, but Dialogflow (intent/slot-based) and an LLM-fallback architecture (Fig. 1) are two different paradigms — the paper never reconciles which one it's actually proposing to build.
  • No vector database, no embedding model, no re-ranking is specified anywhere, despite RAG and FAISS being called out by name in the literature review of other papers (ref. [1]) as best practice.
  • The reference list padding is telling: citations to HTML and CSS: Design and Build Websites, JavaScript: The Definitive Guide, Fundamentals of Speech Recognition (1993), and An Introduction to Text-to-Speech Synthesis (1997) suggest a broad, unfocused reference list rather than a stack that was actually selected and justified for this system.

Net: the concepts referenced (LLMs, OpenAI API, RAG-adjacent ideas via citations) are current as of 2025. But since none of it was implemented, "outdated" isn't quite the right question — the more relevant one is that the stack was never pinned down to specific, testable choices.

03

How was the solution tested?

Not tested — nothing was built

There is no testing in this paper. Section IV ("Results and Discussion") contains no results — it is a discussion of what testing should happen if the system were built: "We'd need to run thorough testing, validation, and keep things updated," "testing to ensure it works well, particularly when it comes to tricky legal questions."

  • No prototype, screenshot, transcript, or demo of the chatbot answering a single question appears anywhere in the paper (contrast with the LAWBOT paper, which at least shows UI screenshots).
  • No metrics — no accuracy, latency, user satisfaction score, or A/B comparison of local-lookup vs. OpenAI-fallback response quality.
  • No user study, pilot group, or DOJ stakeholder involvement is described, despite "pilot phase" being mentioned as an intention in the introduction.
  • The "95% accuracy" figure that appears in the paper belongs to a different, cited paper (ref. [10], the AI-Enabled Chatbot Framework for citizen-government services) — it is not this paper's own result, and it's easy to misread it as such on a skim.

Implication

Every "advantage" and "outcome" claimed in this paper (24/7 access, personalized help, boosted efficiency) is aspirational, not measured. This is best read as a project proposal or requirements document, not an implementation report.

04

What datasets were used?

None

No dataset — legal, FAQ, or otherwise — is named, sourced, sized, or described anywhere in the paper. The "knowledge base filled with relevant legal documents, frequently asked questions, and procedural guides" mentioned in the introduction is described as something that would be built, with no indication of what documents, how many, from where, or in what format.

This stands in contrast to essentially every paper summarized in its own literature survey (Section II), most of which name a concrete corpus, intent count, or chat-log dataset (e.g. LAWBOT's Indian Kanoon judgments, or ref. [5]'s "custom dataset of 100 chats"). The absence of any equivalent detail here is a significant gap for a paper about a specific, named government website.

05

Plus points of the research

  • Broad, current literature survey. 24 chatbot papers (Section II) spanning legal, government-services, healthcare-adjacent, and banking domains gives a genuinely wide field-of-view on 2023–2025 legal/government chatbot work, including non-English sources (Colombian legal-access chatbot, ref. [11]).
  • Correctly identifies the hybrid local-data + LLM-fallback pattern as a practical cost/speed/quality tradeoff — a real, reusable architectural instinct even though it isn't built out here.
  • Explicit human-oversight framing. Repeated emphasis on flagging sensitive conversations for human review, rather than letting the AI answer everything autonomously, is a responsible instinct for a government legal-info tool.
  • Consolidated "gaps" list (Section II, end) is a genuinely useful synthesis — ethical concerns, offline-use limitations, limited UX evaluation, and adaptability issues are all real, recurring problems across the field it surveys.
  • Names concrete, current building blocks (OpenAI API, LLMs, RAG, FAISS via cited work) rather than only legacy NLP techniques, showing awareness of where the field has moved.
06

Gaps in the research

  • Nothing was built. This is the defining gap — nearly every claim about the chatbot's benefits or behavior is speculative, written in conditional/future tense, with no working system to point to.
  • Mismatched/reused architecture diagram. Fig. 2's "Symptoms → Diagnosis" labeling indicates the figure was not created for this project, undermining confidence in how carefully the paper was assembled.
  • No dataset, no data source, no legal domain scoping. "The DOJ's website" is never broken down into what legal topics, jurisdictions, or document types the chatbot would actually cover.
  • Two incompatible architectures presented as one system — Fig. 1 (LLM-fallback) and Fig. 2 (Dialogflow intent-matching) are different design philosophies, and the paper never says which one wins or how they'd combine.
  • Security and ethics are asserted, not designed. "Strong encryption," "fairness-aware algorithms," "regular bias checks" are named as goals with no method, tooling, or evaluation protocol attached.
  • Casual, non-technical prose ("pretty exciting," "game changer," "not all smooth sailing") throughout what's nominally a peer-reviewed engineering paper reduces precision and makes several claims hard to distinguish from marketing language.
  • Reference list padding. Citations to general web-dev and decades-old speech-synthesis textbooks (refs. 19–20, 23–24, 26–27) appear disconnected from the paper's actual legal-chatbot argument, suggesting the bibliography wasn't curated tightly to the claims made.
  • No cost, compute, or latency analysis for the OpenAI-API-fallback design, despite this being a real, non-trivial operating consideration for a public-sector deployment.
07

What to take into "Your Legal"

This paper is weak as an implementation reference, but useful as a checklist of considerations a real deployment needs — several of which the LAWBOT-style papers skip entirely.

Borrow

Local-data-first, LLM-fallback routing

Check a curated internal knowledge base before calling an external LLM. Cheaper, faster, and more controllable for high-confidence answers — reserve the LLM call for genuinely novel queries.

Borrow

Human-in-the-loop escalation for sensitive queries

Build explicit logic to flag queries touching on active cases, emergencies, or high-stakes decisions for human review rather than letting the model answer autonomously.

Implement properly

RAG instead of vague "knowledge base"

Where this paper only gestures at a knowledge base, actually build retrieval-augmented generation over a defined, versioned legal corpus with citations back to source documents.

Borrow

Multilingual support as a first-class requirement

Language selection/detection as an explicit pipeline stage (Section 3.2) is the right instinct for an India-facing legal product — plan for it from the architecture stage, not as a later add-on.

Don't repeat

Publishing an architecture before building it

Design docs are useful internally, but don't let "how it would work" substitute for an actual eval — build a small working slice first, then document what you measured.

Don't repeat

Reused or mismatched diagrams

Every diagram in your documentation should reflect your actual system. A diagram with the wrong domain's terminology erodes trust in the whole document — proofread architecture figures as carefully as code.

Add early

Named, scoped data sources

Decide up front which acts, sections, courts, or FAQ categories "Your Legal" actually covers, and document dataset size/provenance — vague "legal knowledge base" language is a gap you can close before you write a line of code.

Add early

Cost and latency budget for the LLM fallback

If you adopt the local-first/API-fallback pattern, model out expected fallback rate and per-query API cost early — this paper never does, and it's a real constraint on a public-facing legal tool at scale.

One-line takeaway

Use this paper as a requirements checklist (routing pattern, human oversight, multilingual support, security/ethics considerations) — not as an architecture or evaluation reference, since it documents intentions rather than a built and measured system.
