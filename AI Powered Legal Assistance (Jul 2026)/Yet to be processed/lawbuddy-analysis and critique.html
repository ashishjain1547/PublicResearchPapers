Paper Review · IJCRT · Vol 13, Issue 8, August 2025

LawBuddy, Examined

A working critique of "LawBuddy: AI-Powered Legal Chatbot for Case Tracking, Proof Management, and Legal Assistance" — the most feature-complete stack of the three papers reviewed so far, and the least evidence behind it.

Authors

Apeksha G S, Kiran Kumar M, Krushik M G, Suhas A S, Madesha M — PES Institute of Technology and Management, Shivamogga

Venue

IJCRT, Aug 2025

Stated stack

BART · GPT/OpenAI · MongoDB · Firebase/AWS S3 · React Native · Django/Flask

Read this first

Like the DOJ chatbot paper, LawBuddy is a proposal, not a build report: the abstract says the chatbot is "proposed," Section IV is titled "Proposed System," and the "Results" section describes what the system "is bound to" do, not what it did. The tech-stack list is the most detailed of any paper reviewed, but nothing in it is confirmed as implemented, integrated, or working together.

01

Architecture

This is the most layered architecture of the three papers reviewed, spanning five explicit layers (cloud storage/DB, ML, NLP, frontend, backend, auth) plus a single system diagram (Fig. 1) and an 8-step "technical workflow" written in prose.

LayerNamed componentsRole
Storage & DBFirebase / Google Cloud / AWS S3, MongoDBFile storage (evidence/documents) + metadata, profiles, chat logs
MLBART, "Feedback Loop Learning"Case-type forecasting, document categorization, response refinement
NLPspaCy / NLTK / Transformers / OpenAI APIsQuery understanding, NER, intent identification
FrontendReact Native, HTML/CSS/JSMobile + web chatbot UI, file upload handling
BackendPython (Django/Flask), Node.jsQuery routing, NLP-engine communication, API layer
Auth & SecurityJWT/OAuth, SSL, access controlLogin, encrypted transport, document access gating

Fig. 1's actual diagram is much thinner than this list implies: User → Login → MongoDB (fetch user data) → Chat → {Generative Model (summarization), Lawyer Suggestion (MongoDB lookup), Case Tracking → Cloud (Docs)}. It's a legitimate high-level shape — a chat hub fanning out to three services — but none of the five "layers" of technology named in Section IV-A are actually placed on this diagram, so it's unclear which tool does what, or how BART (case-type forecasting) relates to the "Generative Model" box shown.

Read this as

A well-organized technology inventory (six categories, ~15 named tools) paired with one simple, mostly self-consistent flow diagram — but the two were never merged into a single, traceable architecture.

02

How outdated is the tech stack?

Current, off-the-shelf choices One dated/mismatched pick

Taken individually, almost every tool named is a reasonable, current (2025) choice for a legal-chatbot MVP — this paper doesn't suffer from the "pre-LLM" dating problem the LAWBOT paper had.

  • MongoDB, Firebase/AWS S3, React Native, Django/Flask, JWT/OAuth — all standard, current, well-supported choices for a cross-platform app with file upload and auth. Nothing here is stale.
  • OpenAI APIs / Transformers / spaCy / NLTK — a sensible, current NLP toolkit, though naming four overlapping libraries (spaCy, NLTK, Transformers, OpenAI APIs) without saying which handles which task suggests a "kitchen sink" list rather than a chosen pipeline.
  • BART is the one notably dated selection — a 2019 Facebook/Meta sequence-to-sequence model, primarily used for summarization, not case-type classification or forecasting. It's used here (per Section IV-A and cited ref. [3]) for "forecasting attorney case types," which is an odd fit: a classification task would more naturally use a fine-tuned encoder (e.g. a BERT/legal-BERT variant) rather than BART's encoder-decoder generation architecture. This reads like the term was inherited from a cited paper (ref. [3], "AI Chatbot... Assisting Legal Case Prediction") rather than independently chosen.
  • No RAG or vector database is named despite "Legal Knowledge Retrieval" being step 3 of their own workflow — a real gap, since retrieval-augmented generation is the standard current approach for grounding LLM answers in a legal corpus, and it's the single most relevant technique missing from an otherwise current list.
03

How was the solution tested?

Not tested — proposal stage only

There is no evaluation of any kind. Section VI, "Results," contains no numbers, no test cases, no user feedback, and no screenshots — it's written entirely in future/conditional language: "LawBuddy is bound to revolutionize...", "users can receive timely assistance," "LawBuddy also enhances its accuracy... over time".

  • No demo, prototype screenshot, or sample conversation is shown anywhere (a step back even from the DOJ paper, which at least included architecture figures, and well behind LAWBOT, which showed a working UI).
  • The "Feedback Loop Learning" and "Continuous Improvement and Feedback" sections (Section IV-B, step 8) describe a rating/retraining mechanism as a design intention, not something exercised or measured.
  • No claim about lawyer-recommendation accuracy, document-storage reliability, or legal-update-tracking correctness is backed by any test, log, or pilot.
  • The "10 Benefits" list (Section V) and "Results" section (Section VI) largely restate the "Proposed System" section (Section IV) in different words — benefits are asserted, not demonstrated.

Implication

Treat this paper strictly as a system-design proposal. Nothing here constitutes evidence the described pipeline (query → NLP → retrieval → lawyer match → response) has ever been run end-to-end.

04

What datasets were used?

None named

No dataset is named, sized, or sourced anywhere in the paper. The closest the paper comes is describing BART as trained on "large legal datasets" (Section III, summarizing cited ref. [3] — not LawBuddy's own work) and a generic mention of a "legal database" and "law databases or APIs" that the system would query for statutes and case law (Section IV-B, IV-D).

There's no mention of which acts, sections, jurisdictions (Indian Penal Code is referenced only in a single illustrative example — "changes in IPC sections"), lawyer-directory source, or document corpus the system would actually be built on. This is a meaningful gap for a system whose core promise is grounded legal retrieval and lawyer matching — both depend entirely on data that is never specified.

05

Plus points of the research

  • Broadest feature scope of the three papers reviewed. Combines legal Q&A, lawyer matching, secure evidence storage, and law-change tracking into one product vision — LAWBOT and the DOJ paper each cover a subset of this.
  • Evidence/proof management is a genuinely distinct, useful idea not present in the other two papers — tamper-proof, access-controlled storage for FIRs, contracts, and statements addresses a real practical need (chain-of-custody-adjacent) for someone navigating a legal process.
  • Explicit "Existing Systems" gap analysis (Section II) is clearly structured (five named deficiencies: generalist chatbots, manual lawyer search, unsafe storage, no real-time tracking, complexity for non-experts) and gives a legible rationale for each proposed feature.
  • Concrete, current security primitives named — JWT/OAuth, SSL, access control — is more specific than the DOJ paper's vague "strong encryption" language, even though nothing is demonstrated as implemented.
  • Feedback-loop learning concept (users rate responses → retrain model) is a sound, standard MLOps pattern worth carrying forward, even in proposal form.
06

Gaps in the research

  • Entirely unbuilt and unevaluated. The single largest gap — every feature, benefit, and result claimed is aspirational.
  • No dataset specification for the legal knowledge base, lawyer directory, or case-law corpus that every core feature (advice, retrieval, matching) depends on.
  • Architecture diagram and technology list don't map onto each other. Fig. 1 shows a "Generative Model," but Section IV-A lists BART, spaCy, NLTK, Transformers, and OpenAI APIs without saying which one is the diagram's "Generative Model," or how BART's case-forecasting role fits into the chat flow shown.
  • BART misapplied to a classification-shaped task without justification, apparently inherited from a cited paper rather than independently evaluated for this use case.
  • No legal-accuracy or liability framing. Zero discussion of hallucination risk, the difference between legal information and legal advice, or unauthorized-practice-of-law concerns — a real gap for a tool whose flagship example query is "I have been falsely accused of theft, what should I do?"
  • "Real-time" law tracking is underspecified. Section IV-D says the system "periodically scans law databases or APIs," but no source, frequency, or scope is given — "real-time" and "periodically" are used almost interchangeably.
  • No cost or infrastructure analysis despite combining several paid/scalable services (cloud storage, OpenAI API calls, MongoDB) that would materially affect a "cost-effective" claim repeated multiple times in the paper.
  • Literature survey is thin relative to feature scope. Six cited works (mostly generalist legal-advisor bots) support a system that also claims lawyer matching, evidence storage, and law tracking — none of those three features have a directly cited precedent.
07

What to take into "Your Legal"

LawBuddy's value here is as a feature checklist and a stack shopping-list — treat the architecture and results sections as a wishlist to validate, not a blueprint to copy.

Borrow

Evidence/document management as a first-class feature

Secure, access-controlled storage for FIRs, contracts, and statements — tied to the relevant case — is a genuinely differentiating feature none of the other reviewed papers include. Worth scoping properly with real encryption and audit-trail design.

Borrow

Feedback-loop retraining

Let users rate chatbot responses and lawyer matches, and feed that signal back into ranking/retrieval quality over time — a standard, low-risk MLOps pattern worth building in from day one.

Do properly

Retrieval-augmented legal knowledge, not a vague "database"

Where this paper says "retrieves corresponding laws, sections, and tips... from its legal database or trained model," replace that with an actual RAG pipeline over a named, versioned statute/case corpus with source citations in the response.

Validate first

Model-task fit before adopting a named model

Don't inherit "use BART" or any specific model from a cited paper without checking it matches your actual task (classification vs. generation vs. summarization) — this paper's own mismatch is a useful cautionary example.

Borrow

Lawyer matching with real filters

Location, specialization, and experience filters (Section IV-B) on top of case-type matching is a sensible feature shape — just make sure the underlying lawyer directory is sourced, verified, and kept current, unlike here.

Don't repeat

Publishing a stack list as if it were a build

Naming five technology layers doesn't substitute for showing them work together. Before writing up "Your Legal," get one true end-to-end slice (one query → one grounded answer) actually running and demoable.

Add early

Liability and scope framing

Explicitly design for "legal information vs. legal advice" boundaries and flag high-stakes queries (like the paper's own "falsely accused of theft" example) for human/lawyer handoff rather than autonomous AI response.

Add early

Cost modeling across the stack

Cloud storage + vector/DB + LLM API calls add up fast at scale. Model expected per-user cost before committing to a "free/affordable" positioning, since none of the three papers reviewed do this.

One-line takeaway

LawBuddy's differentiator — evidence storage plus lawyer matching plus law tracking in one product — is a genuinely useful scope reference for "Your Legal," but its architecture, tech-stack, and results sections describe intentions, not a working, tested system, so verify every technical choice independently rather than adopting it as-is.
