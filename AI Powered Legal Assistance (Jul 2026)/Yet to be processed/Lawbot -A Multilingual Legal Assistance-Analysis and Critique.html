🧑‍⚖️ Lawbot: Multilingual Legal Assistance Chatbot — critique & analysis

IJSET_V14_issue2_483  |  Gayathri Kodipaka, Kompalli Sri Divya Muktha, K. Sandeep

🏛️ Architecture

High‑level system design – LawBot follows a client‑server (frontend + Firestore) architecture with offline fallback:

  • Frontend: Web app (JavaScript, Tailwind) with dynamic UI localisation (7 Indian languages).
  • Input modalities: Text input + voice input via Web Speech API (speech‑to‑text).
  • Knowledge base: Google Firestore (primary) + local JSON fallback for offline use.
  • Query matching: Tokenisation → keyword overlap scoring (cosine similarity / fuzzy matching).
  • Response delivery: Text + text‑to‑speech (Web Speech Synthesis) with urgency flag & helpline escalation.

✅ Clean separation of concerns, offline resilience, and voice‑first design are commendable. However, the system lacks a true NLP/ML pipeline (no transformer, no intent classifier beyond keyword overlap).

🕰️ How outdated is the used / referred technology stack?

📚 Stack components

  • Firestore – modern, serverless, good choice.
  • Web Speech API – standard, but accuracy varies; fine for demo.
  • Keyword overlap + cosine similarity – classic (pre‑2020); state‑of‑the‑art uses dense retrieval / LLMs.
  • Tailwind / vanilla JS – modern frontend, but no framework (React/Vue) – acceptable.
  • BERT referenced in literature (Phan et al. 2023) – but not used in the actual system.

⏳ Currency assessment

The core matching engine is 3–5 years behind current legal AI practice. While the paper mentions transformer‑based models (BERT) in the survey, the implemented system relies on keyword overlap – which is brittle and cannot handle paraphrasing or complex legal reasoning.

📉 No LLM, no RAG, no fine‑tuned embedding – the approach is rules + keyword based.

🧪 How was the solution tested?

Limited empirical testing – the paper shows screenshots (Figures 1–3) of sample queries (domestic violence, land dispute, Hindi voice input). No quantitative metrics are reported:

  • No accuracy, precision, recall, F1 on a test set.
  • No user satisfaction or usability study.
  • No latency or performance benchmarks.
  • No comparison with baseline systems (e.g., generic chatbots or web portals).

⚠️ The “Results” section is purely qualitative (screenshots). The system is validated via anecdotal demonstration, not rigorous evaluation.

📂 What data sets were used?

The paper does not specify any named dataset. The knowledge base is described as:

  • “Curated Firestore‑backed knowledge base” with keyword–response pairs.
  • Localised responses in 7 languages – but no details on the size, source (statutes, case law, FAQs), or translation process.
  • No mention of public legal corpora (e.g., Indian Kanoon, CaseHOLD, or legal FAQ collections).

❗ The knowledge base appears to be handcrafted and small – not a scalable data‑driven approach.

✅ Plus points of the research

💡 Strong practical vision

  • Multilingual support (7 Indian languages) – directly addresses India’s linguistic diversity.
  • Voice + text – lowers barrier for low‑literacy users.
  • Offline fallback – crucial for rural / low‑bandwidth areas.
  • Urgency escalation – appends helpline numbers for sensitive queries (domestic violence, etc.).
  • Clear ethical stance – empowers citizens, but not a substitute for legal counsel.

🔍 Deployment‑ready thinking

  • Designed for web + mobile – practical reach.
  • Uses Firestore and local JSON – realistic production choices.
  • Good literature survey (BERT, multilingual NLP, speech systems).
  • Proactive future roadmap – LLM integration, more languages, court judgement feeds.

❌ Gaps in the research

  • No ML / NLP model – relies on keyword overlap; cannot handle semantic variations or complex queries.
  • No quantitative evaluation – zero metrics; only screenshots.
  • Knowledge base size & coverage – undisclosed; likely limited to a few hundred FAQs.
  • No user testing – no real‑world deployment or feedback.
  • Translation quality – no mention of how multilingual responses were validated (human translators? MT?).
  • No security / privacy – user queries may contain sensitive info; no encryption or anonymisation discussed.
  • No comparison – with existing legal chatbots or even a simple baseline.
  • Speech recognition accuracy – not evaluated for Indian languages (accents, dialects).

🧠 Ideas to learn and use in “Your Legal” solution

  • Voice + text multimodal – adopt Web Speech API for low‑literacy users; it’s a differentiator.
  • Offline‑first – bundle a local JSON knowledge base for fallback; critical for rural India.
  • Urgency / escalation – flag sensitive topics and provide helpline numbers + actionable advice.
  • UI localisation – dynamic language switching with BCP 47 tags; easy to implement and scale.
  • Firestore as knowledge base – real‑time updates, easy to manage.
  • Future‑proofing – the paper’s roadmap (LLM, court feeds, case tracking) is exactly what “Your Legal” should prioritise.
  • Proactive notifications – legal deadlines / rights reminders via mobile companion app.
  • Build a hybrid system – use keyword matching as fallback for offline, but primary retrieval should be dense embedding + RAG with a fine‑tuned LLM.

🚀 Your Legal can adopt the accessibility philosophy (voice, offline, multilingual) while upgrading the core with modern NLP – transformer‑based intent classification, semantic search, and generative response with citations.

📌 Final verdict: This paper presents a well‑intentioned, production‑aware prototype with strong usability features (voice, offline, multilingual). However, the AI core is rudimentary (keyword overlap) and the evaluation is anecdotal. It serves as a UX/accessibility reference but not as a technical blueprint for legal reasoning. For “Your Legal”, combine the inclusive design principles with a state‑of‑the‑art RAG + LLM backend.
